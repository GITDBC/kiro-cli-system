# Permissions migration

> Migrating from CLI 2.x per-tool rules to the capability-based permissions model in CLI V3

> **New to Kiro CLI V3?** This page covers migration from CLI 2.x. If you're setting up permissions for the first time, start with the [current permissions reference](https://kiro.dev/docs/permissions.md). Without a `permissions.yaml`, Kiro allows workspace reads and common read-only commands, blocks writes to its own settings, and asks before other operations.

Kiro CLI V3 replaces persistent per-tool `toolsSettings` rules with structured `permissions.yaml` policies. The `--trust-all-tools` startup flag and `/tools trust-all` slash command grant session-wide trust. In non-interactive V3 runs, `--trust-tools` can pre-approve exact V3 tool IDs; the interactive V3 terminal UI ignores that flag. Use scoped `permissions.yaml` allow rules for reusable capability policies.

**ℹ️ Info:** Run `/upgrade-agent` to auto-convert compatible permission rules and get a report of what needs manual attention.

The core shift is from per-tool configuration to capability rules that apply consistently across every tool performing the same kind of operation. The rule schema, scopes, effects, presets, and pattern syntax are documented once in [Permissions](https://kiro.dev/docs/permissions.md); this page covers only what changes when you move from 2.x.

## Behavioral changes from 2.x

| 2.x behavior | V3 behavior | Migration |
|--------------|-------------|-----------|
| `toolsSettings` with per-tool allow and deny lists | Unified `permissions.rules` with `capability`, `match`, and `effect` | Rewrite using the [toolsSettings migration table →](https://kiro.dev/docs/cli/v3/migration-guide.md#4-review-remaining-agent-config-fields) |
| `autoAllowReadonly` configured read-only shell approval | Read-only-shell policy generated by `/upgrade-agent` unless legacy `denyByDefault` also applies | Run `/upgrade-agent`, review the generated policy, and add `shell` allow rules for any additional commands you use |
| `denyByDefault` blocked unlisted tool operations | Explicit deny rules, optionally with `exclude` exceptions | Use `` to deny everything except the excluded patterns; see [Exclude syntax](https://kiro.dev/docs/permissions.md#exclude-syntax) |
| Regex patterns in permissions | Glob patterns only (no regex) | Rewrite `.*` as `*`, `\.ts$` as `*.ts`, etc. |
| `?` single-character wildcard for command patterns | Not supported for shell or URL patterns | Use `*` or spell out alternatives. File path patterns (`fs_read`, `fs_write`) still support `?` |
| Read and write restrictions configured per tool | One capability rule applies to every tool that performs that operation | Account for the broader scope of `fs_read`, `fs_write`, and other capabilities; see the capability list under [How it works](https://kiro.dev/docs/permissions.md#how-it-works) |
| Per-tool denies evaluated independently | Deny always wins across all scopes | Remove conflicting allows or narrow the deny pattern |
| A sub-agent's own pre-approved tools ran without prompts, even if the parent didn't allow them | A sub-agent's tool call runs without a prompt only when the parent session's policy also allows it | Add the sub-agent's `allow` rules to the parent agent's `permissions.rules` or to `permissions.yaml`. See [Sub-agent permissions](https://kiro.dev/docs/custom-agents/subagents.md#sub-agent-permissions) |

## Session-scoped commands

These controls apply only to the current session:

```bash
# Trust every tool in a V3 session
kiro-cli chat --v3 --trust-all-tools

# In headless V3, trust exact tool IDs
kiro-cli chat --v3 --no-interactive --trust-tools=read_file,grep_search "Review this repository"

# In interactive V3, trust every tool after startup
/tools trust-all
```

In V3, `--trust-tools` is honored only with `--no-interactive` and matches tool IDs; in Kiro CLI 3.3.0 or later it also accepts V2 tool names, `@server` references, and `*`/`?` patterns (see [Headless mode](https://kiro.dev/docs/cli/headless.md)). The interactive V3 terminal UI ignores it. CLI 2.x accepts its own tool names. For reusable or capability-level rules, use `permissions.yaml`.

## Persistent rules

Create `~/.kiro/settings/permissions.yaml` for user-scoped rules, or a workspace-scoped file at `~/.kiro/workspace-roots/<hash>/permissions.yaml` to scope rules to one project. Workspace files are stored per-user outside the repository, so a cloned repo cannot inject permission rules. For the file format, scopes, and worked examples, see [Defining rules](https://kiro.dev/docs/permissions.md#defining-rules) and [Scopes](https://kiro.dev/docs/permissions.md#scopes).

## Approve for me

Approve for me and its `evaluate` effect are documented in [Permissions](https://kiro.dev/docs/permissions.md#approve-for-me). They are not a migration step: no 2.x setting maps to them.

## Approval rule tiers

The three-tier rule picker that appears when a V3 session asks about a shell command is documented in [Permissions](https://kiro.dev/docs/permissions.md#approval-rule-tiers). CLI 2.x had no equivalent picker.

## CI and headless environments

For CI pipelines that previously used `--trust-all-tools`, create a user-scoped permissions file in your CI environment:

```yaml
# ~/.kiro/settings/permissions.yaml (CI environment)
rules:
  - capability: all
    effect: allow
```

The `--trust-all-tools` flag still works as a session-scope override and continues to function for CI use cases without configuration changes.

A headless run denies sub-agent tool calls that the parent session's policy doesn't allow, even when the sub-agent's own rules allow them. `--trust-all-tools` approves sub-agent tool calls that would otherwise prompt. `deny` rules still apply.
